## 以收帧时间限制续期

- 实验模式为每路最多容许两帧待处理。续期仍使用已有的通过证据，最迟截止取原证据期限、最早的待处理帧采集及接收期限以及当前 70 ms 的上限。缺失序号、超时、更多积压和故障禁止续期。测到近处障碍会锁存，覆盖不足的帧不能刷新雷达证据。ROS 锁或协调器忙时控制线程立即返回等待。回归测试用真实 RelayGate 验证旧证据到期会转零，也验证复核成功前维持旧命令的截止时间。
- 起步采用完整同步复核，使用通过的同一份证明初始化两个复核线程，保留首条指令的原始截止时间。续期以当前各通道的期限为准。新雷达证明只有在通过新帧和旧射线的覆盖复核后才能代替旧覆盖期限。首条指令和未分离的模式保留原有条件。

- 厂商给出了样本字中的干扰标志定义。当前设备在旧 SDK 中报告型号代码 3，并且两项抗干扰标志均未声明。单独将这种低位模式当未知的只读试验消除了近距拦截，同时使完整前向通过数从 140/154 降为 35/246，主要失败项为前向覆盖不足。该模式未部署，已恢复现有雷达进程。样本证据保存在 `~/rosclaw/jev/evidence/nav-runs/lidar-return-20261121-1038`。 [YDLIDAR X2 开发手册](https://www.ydlidar.com/static/upload/file/20260615/1781511796261548.pdf) [厂商 SDK 标志定义](https://github.com/YDLIDAR/YDLidar-SDK/blob/master/core/common/ydlidar_protocol.h)
- 复测的 Release 构建最初在初始化时触发了单通道元数据解析的缓冲区检查。原因是 SDK 把八位序列号片段及其终止符写进仅剩八字节的字段。补丁 `patches/ydlidar-single-channel-metadata.patch` 修复该处，并校验序列号末片段。修复后以 Release 驱动实车采集并恢复 `/scan`。本轮在停车状态执行，连续导航仍待验收。
- 恢复原雷达输出后，`trial-native-depth-20261121-105335` 的 Decisions 选择 `forward`，起步后台复核再次触发 `front_blocked`。非零速度 0 条，试验结束后 `/cmd_vel` 无发布者。
