# LIMO 深度投影标定检查

## 发现

- 本机 `dabai_u3.launch` 默认启用 `depth_align=true`，彩色流为 640×480，深度流为 640×400（`~/agilex_ws/src/ros_astra_camera/launch/dabai_u3.launch` 第 5、13–20 行）。
- 车上此前的实时观测显示 `/camera/depth/image_raw` 的 frame 是 `camera_color_optical_frame`，大小 640×400；`/camera/depth/camera_info` 的 frame 是 `camera_depth_optical_frame`，大小 640×400；彩色标定为 640×480。该观测来自 2026-11-17/18，只证明当时的数据，不保证当前状态。
- 驱动把深度对齐后的图像帧设为彩色光学坐标系（`ob_camera_node.cpp` 第 506、771–772 行），但深度标定由 `getDepthCameraInfo()` 生成（第 124、781 行）。初始化发布的深度 CameraInfo 采用深度光学 frame（第 133 行）。这解释了为什么需要核对每一对图像和标定；单靠字段或名称不能证明数值正确。
- `point_cloud_xyz.cpp` 第 59、73、82 行直接使用深度图的 header 和传入的 CameraInfo 构建点云。因此现有点云也不能跳过对标定与对齐方式的核验。
- 本轮只读复测时，深度图仍为 `camera_color_optical_frame`，640×400；取得的深度 CameraInfo frame 为空，时间戳较该次读取时刻旧约 28 秒，`R` 也不是单位矩阵。由于采样并非同一个同步对，这只能作为问题线索，不能据此计算外参或判断全部帧都如此。固定话题采集器对这些不一致按失败处理。
- 随后的只读复测采用雷达、深度图和 CameraInfo 的近似时间同步，匹配到的一组数据中，深度图 frame 是 `camera_color_optical_frame`，CameraInfo frame 为空，二者均为 640×400。因此这次拒绝是 frame 不匹配，而非图像尺寸不同；此结果只适用于该组数据，不证明内参或外参精度。驱动逐帧发布路径设置了 CameraInfo 时间戳但没有设置 frame（`ob_camera_node.cpp` 第 779–790 行），与该现象一致；修正 frame 本身仍不能证明 CameraInfo 数值正确。
- 增加只读矩阵诊断后，一组同步数据的 `K` 和 `P` 中 `(fx, fy, cx, cy)` 均为 `(478.022, 478.022, 324.913, 198.602)`；`R` 与单位矩阵逐元素的最大绝对差为 `0.00649188`。`K` 与 `P` 的这几个数相等不证明实际投影正确；`R` 非单位也不单独证明标定错误，但不满足当前仅支持单位校正矩阵的保守投影器要求。诊断仍明确标记不可用于实机运动。
- 固定只读服务 `/camera/get_camera_params` 返回 SDK 左内参 `(478.0223, 478.0223, 324.9125, 198.6018)`，与上述深度 CameraInfo 的 `K` 一致；右内参为 `(488.6276, 488.6276, 318.4415, 206.4526)`，明显不同。深度图的 frame 却被标为彩色光学坐标系。这支持了“对齐深度的图像坐标系和发布内参可能不一致”的担忧；还必须核对设备型号的对齐、裁剪、缩放及 SDK 参数定义，不能仅凭这一差异选择右内参。`R` 数值与 SDK 的 `r2l_r` 一致，但这不证明该矩阵是已对齐深度图所需的矫正矩阵。
- 进一步检查 `ob_camera_info.cpp` 第 323–360 行：`getDepthCameraInfo()` 在 `!isValidCameraParams(camera_params)` 分支内才把对齐流的 `K` 设为彩色内参；函数随后还对部分主点项做了重复/不同下标的偏移。这里**可能**存在对齐内参与图像不一致的问题，也可能依赖硬件和 SDK 的特定约定。仅凭源码不能判定实际投影正确或错误，不能据此直接改驱动。
- 独立副本发现另外两个待验证问题：开启 `depth_align` 时，原代码对所有图像流选择彩色光学 frame，而不只对深度流选择；另外 `setImageRegistrationMode()` 在设备不支持或设置失败时返回，但调用方仍可能保留 `depth_align_` 配置。复制图像 header 修复空 frame 只能解决消息元数据缺失，不能证明实际对齐已成功，也不能证明内参对应图像。隔离补丁未运行或安装到机器人。
- 源码中动态配置回调会更新 `depth_align_` 并重启图像流，但 `setupD2CConfig()` 的静态调用点只出现在初始化路径；尚需查证动态切换后 SDK 的注册模式是否同步改变。配置值和图像 frame 名称都不是设备实际注册状态的独立证据。
- 隔离工作区 `worktrees/ros-astra-camera` 包含候选改动：逐帧 CameraInfo 继承对应图像 header；静态配置下，仅当 SDK 明确报告未对齐时才发布深度原生 frame。SDK 状态未知、已对齐但内参未核实，或启用动态重配置时，深度 frame 留空。收紧后的候选代码在临时 catkin 工作区完整编译，使用模拟设备的状态核验 CTest 通过；候选代码未安装、启动或在相机上验证。它没有修改 CameraInfo 内参或畸变参数，SDK 报告的注册状态也不证明物理投影准确。
- 候选代码现会在要求非对齐模式时先读取设备状态；如果设备仍保留上次的对齐模式，则尝试切回 OFF 并再次读取确认。模拟 SDK 测试覆盖了该转换。现场重启相机前无法知道实际设备是否支持这个切换，也不能因此视为几何标定完成。
- 2026-11-18 相机因 USB 错误停止更新后，已用临时构建的候选驱动、`depth_align=false` 重启。彩色和深度流恢复，深度图与持续更新的 CameraInfo 分别观测到 `camera_depth_optical_frame`；此前采集器只接受彩色光学 frame，需更新后才能再次获取同步投影诊断。临时驱动运行在 tmux 会话 `rosclaw_camera`，这不是已安装发布版本。帧名和更新时间本身不验证几何精度。
- 同日稍后相机在 UVC 停流后再次卡住，内核报告 USB `Ring expansion failed`。候选驱动增加可选 `keep_streaming` 参数，重启并启用后，多次订阅断开没有触发停流，彩色和深度消息持续更新超过 9 分钟；更长时间稳定性尚未验证。诊断采集器已支持原生深度 frame，并在 TF 历史不足时重新采样。一次采集的图像与 CameraInfo 时间一致，与雷达相差约 8 毫秒。
- 后续三帧只读对照均采集成功；在主要为 4–6 米的雷达点上，相机内参候选的逐帧绝对残差中位数约为 1.20 米，深度图有效像素比例中位数约为 26%。这些帧彼此相关，且 TF、视差、遮挡、深度量程和相机标定均未独立核验，不能据此断定具体误差来源，也不能将其用作运动许可。

## 必须完成的验证

1. 重新采集同步的 depth image、CameraInfo 和 TF，核对 frame、分辨率、内参、裁剪/缩放与驱动发布方式。记录传感器型号、配置和时间。
2. 在多个已知位置、距离和高度放置参考物，比较投影点与机器人坐标系中的实测位置；确认外参、地面高度和误差边界。不能只依赖一张视觉图或单一像素。
3. 将地面、悬崖、透明物体、低矮障碍及相机/雷达盲区纳入覆盖验证；缺测始终是未知，不得标为可通行。
4. 真实执行器只能消费经守护进程独立采集和验证的数据。当前几何函数使用调用方输入，仅用于离线回放，不能给真实运动授权。

本轮已复现图像与标定元信息不一致；尚未完成同步采集和实际投影精度复核。不得为让测试通过而改写 frame、缩放内参或自行假定两个图像坐标系相同。
